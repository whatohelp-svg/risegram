# RiseGram MTProto server

This directory pins the independent MTProto server implementation in
`mtproto/` as a Git submodule. The pinned upstream revision is
`18511c2227b3cf4f4006ea3fc63ac10910f55530` from
[iamxvbaba/gramsrv](https://github.com/iamxvbaba/gramsrv), licensed Apache-2.0.

This server speaks Telegram's MTProto protocol and is the server-side protocol
endpoint for a patched Telegram Android client. It is separate from the
existing RiseGram Python REST API and its SQLite database. Do not point the Go
server at the Python service's `risegram.db`: the MTProto server requires its
own PostgreSQL and Redis state.

## Start the MTProto stack locally

1. Clone RiseGram including both submodules:

   ```sh
   git clone --recurse-submodules https://github.com/whatohelp-svg/risegram.git
   cd risegram/server
   ```

2. Copy `.env.mtproto.example` to `.env.mtproto` and replace every
   `CHANGE_ME` value with unique random secrets. Set
   `TELESRV_ADVERTISE_IP` to a client-reachable IP. Never use the development
   login code on a public server.

3. Build and start the independent MTProto service, admin panel, and dedicated
   dependencies:

   ```sh
   docker compose --env-file .env.mtproto -f docker-compose.mtproto.yml up -d --build
   ```

The MTProto listener is TCP port 2398 by default. The RiseGram Docker build also supports `TELESRV_ADVERTISE_PORT` so a TCP proxy with a generated external port can advertise that external port in `help.getConfig.DCOptions` while the process continues listening on 2398 internally. The admin panel is exposed on TCP port
2600; put it behind HTTPS and restrict access before publishing it. The
server generates its own persistent RSA private key under the mounted
`/var/lib/telesrv` volume on first boot. Back up that volume; changing the RSA
identity breaks clients that pinned the previous public key. PostgreSQL, Redis,
media blobs, server identity, and keys are persisted in named volumes.

The Compose stack intentionally does not start the old Python API or Telegram
bot. Those remain separate RiseGram services and keep their existing SQLite
volume. No data is deleted or migrated by this stack.

## Client connection

A stock Telegram Android binary uses Telegram's production data-center list
and RSA fingerprints. It must be built as an unofficial RiseGram client with
its DC address and the public RSA fingerprint generated by this server
configured in the client. The public endpoint is the host/port that forwards
TCP to container port 2398; the private RSA key must never be copied into the
APK.

The upstream server project documents client compatibility and API behaviour:
https://github.com/iamxvbaba/gramsrv

## Current integration boundary

This adds a real MTProto protocol server, not merely a REST compatibility
shim. The MTProto server has its own user/account store. RiseGram's existing
RiseStars/GRAM economy and legacy account records remain in the Python SQLite
service until an explicit account-identity and economy bridge is implemented.
The Telegram Android source is pinned separately at
`../client/telegram-android`; the matching DC and RSA settings and login-code
delivery still need to be connected in the client/server configuration.
